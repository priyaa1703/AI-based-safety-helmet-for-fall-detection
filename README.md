# Miner Safety Helmet - ML part

A small MLP (10 -> 32 -> 16 -> 4) that classifies a miner's condition from
10 sensor values, then gets squeezed to an INT8 TensorFlow Lite model
(about 4.8 KB) for an ESP32.

> **The dataset is synthetic.** `data/helmet_sensor_dataset.csv` was generated by
> `generate_dataset.py` so the pipeline can be built and tested before any real
> helmet data exists. The accuracy numbers below say the *code works*. They say
> nothing about how the helmet will perform on a real miner. Please keep that
> label on the dataset if you show or submit this project.

## Quick start

    pip install -r requirements.txt
    ./run_all.sh          # or run the scripts below one by one

| Script | What it does |
|---|---|
| `generate_dataset.py` | makes `data/helmet_sensor_dataset.csv` (8,000 rows) |
| `preprocess.py` | cleaning, label encoding, stratified 80/20 split, imputer + scaler fitted on train only |
| `train_mlp.py` | trains the MLP, saves `models/helmet_mlp.keras` and the curves |
| `evaluate_model.py` | test-set metrics, confusion matrix, feature importance |
| `convert_tflite.py` | INT8 conversion, size/accuracy comparison, writes the C headers |

## Feature and class order (do not change)

    [AccX, AccY, AccZ, GyroX, GyroY, GyroZ, HeartRate, SpO2, Temperature, Humidity]
    units: g, g, g, deg/s, deg/s, deg/s, bpm, %, deg C, %RH

    class ids: 0 NORMAL, 1 FALL, 2 HEALTH_ALERT, 3 ENVIRONMENT_ALERT

## Dataset

8,000 rows: NORMAL 4439, HEALTH_ALERT 1190, FALL 1187, ENVIRONMENT_ALERT 1184.

Classes overlap on purpose: hard-working normal miners have high heart rates,
some normal readings come from warm sections, soft falls have weak impacts,
a few falls also have bad vitals, and about 1.5 % of labels are flipped.
~0.5 % of values are missing and ~26 are sensor glitches (HR = 0 / 255,
SpO2 = 0 / 127, temp = -127) so the cleaning step has something to do.

One honest simplification: each row is a single instant, so a fall is sampled
either as the *impact* moment or the *lying still afterwards* moment. A real
helmet would look at a short window of readings (see "Next steps").

## Results (test set, 1,600 unseen samples)

| Model | Accuracy | FALL recall | Size |
|---|---|---|---|
| Keras float32 | 0.8975 | 0.886 | - |
| TFLite float32 | 0.8975 | 0.886 | 5,980 B |
| TFLite INT8 | 0.8981 | 0.890 | 4,856 B |

The INT8 model is one sample "better" than float, which is just rounding noise,
not an improvement. Quantization cost essentially nothing here.

Per class (F1): NORMAL 0.915, FALL 0.894, HEALTH_ALERT 0.836, ENVIRONMENT_ALERT 0.890.

Training hit the 50-epoch cap with validation loss still falling very slowly,
so a longer run might gain a little. I kept your 50-epoch limit.

### FALL: missed falls vs false alarms

27 of 237 falls were missed (11.4 %), 23 normal/other samples were flagged as FALL.
A missed fall means an injured, maybe unconscious miner and nobody gets told,
so the delay can cost a life. A false alarm costs a supervisor a quick check.
That's why the sketch alerts when P(FALL) >= 0.30 even if FALL isn't the top class:

| threshold | FALL recall | false alarms |
|---|---|---|
| argmax (0.5) | 0.886 | 23 |
| 0.30 | 0.924 | 39 |
| 0.20 | 0.932 | 55 |
| 0.10 | 0.970 | 84 |

Also, 213 of 237 falls triggered *some* alert even with plain argmax.

## Analysis

**Most useful features** (permutation importance): HeartRate, Temperature,
Humidity, AccZ, AccX and SpO2 all matter for overall accuracy, which makes sense
since each one defines a class. For FALL specifically, only AccX and AccZ
matter a lot (recall drops ~28 points when either is shuffled). The gyro axes
are weak here, partly because my generator made fall motion mostly visible in
acceleration.

**Common confusions:** HEALTH_ALERT -> NORMAL (46), ENVIRONMENT_ALERT -> NORMAL (29),
FALL -> NORMAL (24). Almost all errors are alert-vs-NORMAL, which is expected,
because borderline values (a fast but healthy heart rate, a warm tunnel, a soft
landing) sit right at the boundary. Alert classes are rarely confused with each other.

**Is the dataset realistic enough?** Enough to develop and test the pipeline,
no more. The value ranges are plausible, but I chose the distributions, so the
model is learning *my* assumptions about miners. Real data will behave differently.

**Limits of synthetic data**
- No real sensor quirks: drift, motion artefacts in the pulse oximeter,
  loose-fit helmets, humidity sensor lag.
- No real fall dynamics, and no look-alikes such as dropping the helmet, 
  sitting down hard, or hitting a rock with the helmet while standing.
- No variation between people or between mines.
- Class balance is invented; real falls are far rarer than 15 %.
- Rows are independent snapshots; real data is a time series.

**When you switch to real ESP32 data**
1. Log raw readings with timestamps and labels, in the same units and feature order.
2. Collect many people, shifts, mines; split train/test **by person or by session**,
   not by random row, or you'll get leaked, inflated results.
3. Safe fall data is hard: use staged falls (mats, dummies) and treat results cautiously.
4. Move from single rows to windows (e.g. 1-2 s of motion -> max |acc|, std,
   post-impact stillness) and retrain. That will change the input size, so
   update the headers and the sketch.
5. Refit the scaler and imputer on the new data and regenerate both headers
   (`python convert_tflite.py` does it).
6. Check the real MAX30102 HR/SpO2 quality, and the sensor ranges
   (`VALID_RANGE` in `preprocess.py`).
7. Re-pick the alert thresholds from real false-alarm and miss rates.
8. Keep a simple rule-based backup (e.g. very large acceleration -> alert). 
   A tiny ML model should not be the only safety layer in a mine.

## ESP32

Copy `esp32/helmet_inference.ino`, `helmet_model_data.h` and `helmet_scaler.h`
into one Arduino sketch folder. The sketch uses stubbed sensor reads, so you
need to plug in your actual drivers. I could not compile or run the sketch on
hardware here; the model itself was verified in Python through the TFLite
interpreter, including the INT8 input/output scaling the sketch repeats.
The TFLM include paths depend on which Arduino library you install.
